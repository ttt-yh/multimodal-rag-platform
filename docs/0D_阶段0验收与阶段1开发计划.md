# 0D：阶段0验收与阶段1开发计划

日期：2026-09-24。结论：**具备进入阶段1开发的基础条件，但不等于完整RAG已实现、解析质量全部合格或全量入库已获批准。** 最新结果见[0D验收报告](../evals/results/stage0d/report.html)，原页和模型回答见[0C对照报告](../evals/results/stage0c/report.html)。

## 1. 本次验收了什么

本轮重新运行应用测试、原数据回归和真正的本机HTTP启动检查，并只读连接项目专用PostgreSQL，核验基础表及迁移校验和。另对已有0B真实接口记录和0C原始解析包进行哈希复核，从ZIP离线重新生成统一元素，与原结果逐项比较。没有新调用解析、视觉、Embedding或其他模型，也没有执行数据库迁移、创建知识索引或修改旧工程。

本次结果：**155/155项应用测试、29/29项数据测试、8/8项实际HTTP检查、121/121项历史证据与离线复现检查通过**，项目库表和迁移哈希检查通过。这些是工程验收结果，不是模型问答准确率。

| 验收对象 | 检查方式 | 不能据此宣称的能力 |
| --- | --- | --- |
| 工程与代码 | 单元/接口测试、实际启动HTTP后访问健康检查及文档预览，再停止临时服务 | 不代表有问答前端或完整业务链路 |
| 数据 | 数据测试、固定样本/原始资料哈希、开发集归属 | 不代表180条中文候选已人工审核 |
| PostgreSQL | 只读核验专用库、基础表和迁移哈希 | 不代表已实现Chunk、处理版本或索引发布 |
| 模型与解析服务 | 核验历史原始调用记录，检查当前模型配置与已验证记录一致 | 不是本轮新调用或服务持续可用保证 |
| PDF统一元素 | 18份ZIP离线重放，验证20页和400元素来源结构、图像引用及结果一致性 | 不代表OCR全文、阅读顺序或表格全部正确 |
| 质量规则 | 新增纯函数及回归测试；对0C样本进行规则回放；1B worker 已接入单文档处理；审核事件可持久化 | 尚未接入审核页面和版本发布，不能称为完整入库门禁 |

运行快照包含应用和数据JUnit、实际HTTP预览、接口OpenAPI、核心模型JSON Schema、配置、依赖锁及代码哈希。业务库版本本轮实查为PostgreSQL 16.15，未写入任何业务数据。`/health/ready`仍返回503，这是完整检索问答尚未就绪的真实状态，而不是服务启动失败。

## 2. 固定下来的开发边界

继续使用四层模块化单体：API接收请求，application协调用例，core保存核心模型与规则，infrastructure实现存储及外部调用。PostgreSQL作为文档、版本、任务和来源关系的权威存储；Chroma承载向量索引；bm25s承载可落盘的关键词索引；原文件与图像放在受控本地目录。**后两种索引目前尚未接入，不需要现在安装Elasticsearch。**

模型沿用已验证配置：对话qwen-plus、视觉qwen3-vl-plus、Embedding text-embedding-v4（1024维）、重排qwen3-rerank，PDF解析使用MinerU vlm。每次处理记录实际配置；供应商可变模型别名不当成永久不可变模型版本。未来若更换Embedding模型或维度，要建立新的索引版本，不能混写。

首版开发按“文本行号、PDF物理页号、独立图像引用”提供溯源；原始bbox保存但不冒充经过验证的区域坐标。区域定位属于后续独立验收能力，不阻止先开发页级引用。MD及同源PDF只选一个主输入版本，原始MD优先；不能把同一内容的格式副本重复入库，也不能把评测问答、参考答案或官方预解析结果当成语料。

## 3. 解析质量怎样处理

质量规则实现在`core/quality.py`，版本为`parser-quality-v1`。它只给出判定，不联网、不写数据库、不自动批准内容。处理任务“执行成功”和知识内容“可发布”必须分开：解析器成功返回并不代表可以激活该文档。

| 状态 | 触发情况 | 阶段1应采取的行为 |
| --- | --- | --- |
| `blocked`：阻断 | 来源结构不合法、页映射缺失、图像资源缺失、没有可索引元素等 | 保存错误与原始结果，不构建可发布版本；修正后重新校验 |
| `needs_review`：需复核 | 空正文、未知类型、图表没有数值转写，或已知命令失真等内容问题 | 原文件和产物保留为草稿，展示原因；复核/修正/明确排除范围后再决定发布 |
| `candidate`：候选 | 未发现已知结构问题 | 可继续后续构建检查；不是内容准确率通过，也不是人工审核通过 |

本批18份解析结果中，**8份需复核、10份为候选，没有来源结构阻断样本**。这不是10份正确、8份错误的准确率统计：21个空正文是待核查信号，不能直接等同于21段真实内容被遗漏。原文命令失真、品牌名误识别和视觉补写仍需按具体证据处理。

几条确定的规则是：不一律过滤header，因为截图控件会被误标为页眉；不执行提取出来的命令；图表保留原图和标题，数值需要读图时显式说明；VLM描述与原始转写分开保存，不能让生成内容覆盖原文。本次8道视觉题的复核仍由助手完成，完整回答证据一致性5/8，不把核心要点8/8包装为整体正确率。

这些规则已接入1B单文档worker，审核事件可以通过接口写入，但仍未接入审核页面和知识版本发布流程，**不能自动批准或激活内容**。

## 4. 阶段1按四个小批次推进

### 1A：内容版本、处理版本与任务落库（已完成）

第一步补齐入库数据模型和持久化。当前`001_ingestion.sql`只有文档、内容版本、元素和任务基础表，不直接修改已执行的迁移，新增`002`迁移。文档内容没变但解析器、切分参数或提示词变了，应保持原内容版本，生成新的处理版本；索引发布再使用独立的知识版本manifest。这样不会被现有“同文档＋内容哈希唯一”约束卡住，也能保留不同处理结果作比较。

实现本地文件登记、内容哈希去重、处理配置指纹、幂等任务创建与查询，保留`pending/running/succeeded/failed`执行状态，另外记录质量状态和当前处理阶段。重复请求返回原任务，不能生成重复有效记录。解析元素的序号必须在所属处理版本内稳定唯一；0C片段中的局部顺序和样本ID只是验证数据，不能原样充当正式整文入库编号。

**验收：**迁移可重复执行；同输入同配置复用、同内容新配置产生新处理版本；事务失败可回滚；新旧数据隔离；数据库测试使用隔离库。先实现MD/TXT登记与本地解析持久化，不调用新模型、不写Chroma，用户项目库迁移在执行前说明范围。

本批已新增`002_processing_versions.sql`和`003_element_processing_identity.sql`，并在项目专用PostgreSQL 16.15上完成应用。`003`补充处理版本级元素唯一性及`index_eligible/excluded_reason`字段；已应用迁移文件不再修改，只通过新增迁移演进。真实项目库验证了同输入同配置的幂等写入、配置变化产生新处理版本、元素JSON回写和任务唯一键约束。当前只持久化解析预览结果，质量状态可为`candidate/needs_review/blocked`，发布状态保持`draft`，没有自动激活知识版本。

### 1B：单worker、解析持久化与质量复核（已完成）

在任务落库基础上实现一个独立worker，从PostgreSQL领取任务，持久化阶段、租约/心跳和远端批次编号。先用离线夹具验证完整状态流，再在独立开发验证命令中复用已有0C结果包测试适配，不能把预先计算好的结果伪装成新解析调用。真实新文档处理必须使用真实接口，预算不足时明确停止，不偷偷切到Mock。

当前已完成任务租约数据库字段和单worker生命周期函数：`claim_next_job`使用行锁与`SKIP LOCKED`领取待处理或已过期任务，`heartbeat_job`续租，`finish_job/fail_job`只允许持有租约的worker更新结果。`ingestion_worker.py`已将本地白名单Markdown/TXT接入“排队→领取→解析→质量判定→持久化→完成/失败”单次循环，并在真实项目库冒烟通过。新增`GET /api/v1/ingestion/jobs/{job_id}`任务查询和`POST /api/v1/processing/{processing_version_id}/review`审核接口，审核事件写入`quality_reviews`且发布状态仍为`draft`。数据库迁移为`004/005`。

接入0D质量规则：原始响应、元素、资源与警告一并保存；需要复核的文档不能被自动标为发布完成。提供上传/状态/解析对照的最小Web页面和明确审核记录。中断后查询已有远端任务，不盲目重新提交。VLM增强仅针对有必要的图表，限制调用次数和输出，保存模型、提示词版本与费用用量。

**验收：**重启不丢任务状态；已知批次可续查；非法资源和来源缺失阻断；空正文可见且不当成已批准；未经审核的模型描述不覆盖原始证据。

### 1C：结构切分与双索引构建（切分基线已完成，索引待接入）

以已解析元素为输入，按标题/章节形成文本单元，超长单元递归切分，同章节内合并小块；表格保留表头和单位，图像单元关联原图、图题及独立生成描述。沿用600 Token上限、80 Token重叠和100 Token小块参考阈值，但必须先选择并记录可复现的长度统计器；未验证Tokenizer时不能把字符数叫Token数。保留Chunk到Element及原文位置的映射。

当前已实现`core/chunking.py`和`mrag.chunks`持久化：先按`heading_path`形成连续章节，再以字符数硬上限递归切分；Chunk保存元素编号、来源定位和`length_unit=characters`，重复写入幂等。真实项目库已应用`006_chunks.sql`并验证单个处理版本的20个Chunk可重复写入。`007_index_versions.sql`已建立索引版本元数据表；当前处理版本已用2次Embedding API请求生成20个1024维向量，Chroma与BM25s均成功构建，数据库与manifest计数一致，索引状态仍为`draft`。这只是小批验证，全量语料尚未入库或建索引。

增加Chroma与bm25s适配器及锁定依赖。两个索引从同一批Chunk构建，记录模型维度、分词器和处理配置，不在启动时重建全部关键词索引。先验证小批开发资料的真实Embedding，再分批扩展已备语料；已有完整数据无需反复下载。每批API调用另设明确范围及预算。

**验收：**正文边界和来源可回查；重叠去重可解释；两路索引Chunk集合一致；重启后可加载；失败不污染当前活动版本。此阶段可做检索冒烟检查，但还不是完整RAG问答。

### 1D：知识版本激活与入库验收（门禁与检索基线已完成）

先写未激活的Chroma集合、BM25文件及manifest，检查文件完整性、数量、维度和来源映射，再用PostgreSQL事务切换活动知识版本指针。文件系统和Chroma不参与同一数据库事务，不能宣称“跨系统原子写入”；通过不可变产物、完成校验后切换指针保证读侧不混版本。失败留下可诊断草稿，旧版本继续可用，不自动删除旧原文和历史引用。

当前已实现激活门禁：处理版本必须为`approved`，Chunk/向量/BM25数量必须一致，产物目录必须存在；不满足条件时返回错误且不改变活动版本。已实现Dense、BM25和RRF读取函数，并用本地20个Chunk完成三路检索冒烟。当前处理版本曾被审核为`blocked`，因此激活调用被正确拒绝，索引保持`draft`。后续需要对通过审核的处理版本执行知识版本激活，再接入查询Embedding和Rerank。

**验收：**更新、失败、恢复和版本切换流程有自动化测试；未通过质量审核的文档不发布；页面能展示任务、版本、来源与警告。形成阶段1指标报告，再进入阶段2的Dense＋BM25混合召回、RRF融合、Rerank、图文证据组装和引用回答。
