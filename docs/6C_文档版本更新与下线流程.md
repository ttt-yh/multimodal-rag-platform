# 文档版本更新与安全下线

## 目的

知识库资料会持续更新，也可能因为过期、错误或授权变化需要下线。本项目不直接覆盖历史原文，也不直接修改当前 active 索引，而是将更新和下线都作为可追踪的版本变更处理。

## 更新流程

网页上传文件后，服务端会校验文件名、格式、大小、编码或 PDF 签名，并将原文保存到受控的内容寻址目录。相同知识库中的同名文件使用稳定的文档编号，内容哈希变化后产生新的文档版本和处理版本。Markdown/TXT 会进入后台 Worker，PDF 仍需人工确认 MinerU 调用预算。旧版本不会被覆盖，新的处理版本必须重新审核并构建索引。

## 下线流程

通过 `POST /api/v1/documents/{document_id}/retire` 提交操作人、原因和确认标记。系统会：

1. 在 `document_retirements` 写入审计记录；
2. 将该文档的原文版本和处理版本标记为 `retired`；
3. 保留原文、Element、Chunk、索引产物和历史审核记录；
4. 保持当前 active 索引不变，并返回“需要重建索引”的状态。

随后通过 `POST /api/v1/indexes/build` 使用 `build_mode=rebuild_without_retired` 构建排除退役文档的新索引。激活门禁只允许在被移除的处理版本对应原文确实为 `retired` 时发生范围缩减；如果只是误传了一个缺失文档的索引，激活仍会被拒绝。新索引激活成功后，旧索引才退役，问答检索范围随之更新。

## 设计边界

- 下线是逻辑下线，不是物理删除，便于审计和必要时恢复。
- 新索引构建失败不会影响当前可读索引。
- 当前实现为单机 PostgreSQL + 本地索引产物，不引入分布式任务队列。
- 恢复已下线文档时，应重新提交文件、重新审核并构建新的索引，不直接修改历史状态。

## 相关接口

```text
POST /api/v1/ingestion/uploads
POST /api/v1/documents/{document_id}/retire
POST /api/v1/indexes/build  (build_mode=rebuild_without_retired)
POST /api/v1/indexes/{index_version_id}/activate
```
