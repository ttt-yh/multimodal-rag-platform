# 阶段1E：混合检索链路与真实验证

## 目标

阶段1D完成的是“索引可发布”，阶段1E开始验证“查询是否能从已发布索引取回证据”。本阶段只实现检索，不让聊天模型生成答案，便于先观察召回内容、来源定位和排序是否正确。

## 一次查询的流程

```text
查询文本
  ├─ text-embedding-v4 → 查询向量 → Chroma Dense召回
  └─ 本地BM25s索引 → 关键词召回
                 ↓
              RRF融合
                 ↓
       Chroma恢复Chunk原文与来源
                 ↓
       qwen3-rerank重排（失败则回退RRF）
                 ↓
  Chunk文本 + 标题路径 + 源文件 + 行号
```

数据库中的 `index_versions.status='active'` 是唯一发布依据，服务不会读取 `draft` 或 `retired` 索引。Chroma负责向量和Chunk文本/元数据，BM25s从磁盘加载同一批Chunk的关键词索引；RRF只使用两路排名，不比较两种分数的量纲。重排候选默认最多20条，真实调用预算默认是一次Embedding和一次Rerank。

## 真实验证结果

命令：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m multimodal_rag.cli retrieve `
  --query "数据库连接超时时应该检查哪些配置？" --confirm-live --max-requests 2
```

本次使用已激活索引 `idx_f772...`，Embedding和Rerank均返回HTTP 200，最终返回5个带 `source_path`、`heading_path` 和行号的Chunk。完整脱敏记录保存在 `evals/results/retrieval/`。这证明链路和来源映射已经打通，不等价于检索质量评测通过；当前索引只有20个开发样本，后续需要扩大语料并使用带标准证据的评测集计算 Recall@K、MRR 和无答案拒答率。

## 学习时重点观察

1. Dense和BM25各自返回排名，RRF只负责把两个排名合成候选集。
2. Rerank的输入是查询和候选Chunk原文，输出是候选下标及相关性分数，应用层再映射回Chunk来源。
3. Rerank不可用时不重建索引，服务返回 `degraded=true` 并使用RRF前 `final_top_k` 条结果。
4. 本阶段没有把检索结果写入会话记忆；这些候选只供当前请求后续的Context Builder使用。
