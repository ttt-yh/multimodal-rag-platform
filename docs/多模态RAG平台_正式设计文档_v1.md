## 1. 项目定位与边界

### 1.1 项目解决什么问题

企业和团队的知识不仅存在于 Markdown、TXT 等文本中，也存在于 PDF 正文、扫描页面、表格、架构图和操作截图中。仅提取文字容易丢失表格行列关系、图中连接关系和原始位置，导致资料虽然入库，回答所需证据却未被完整保留。本项目构建一套独立的多模态知识平台，完成文档解析、图文关联、知识检索和带来源的问答，并通过评测验证每次改进。

首版以**文字问题检索图文资料**为主要使用方式。系统用可检索的文字表示定位证据，在需要时读取原图，由视觉模型结合上下文理解图表，最终输出能够回到原文核查的答案。

### 1.2 与旧工程的关系

完整保留相邻的旧工程 `rag-diagnosis-agent`，新工程不直接移动其代码、配置、数据和数据库对象。允许在后续实现阶段有选择地复用其结构感知切分、混合检索、模型适配及测试经验，复用模块必须在新工程中独立验证。

本项目负责“文档如何转化为知识、如何检索和回答”。旧项目继续负责“测试任务如何通过工具和工作流完成异常诊断”。未来通过检索接口连接，不要求本轮同步改造旧工程。

### 1.3 第一版范围

| 必须完成 | 首版边界 |
| --- | --- |
| 文档管理 | 多文档上传，支持 PDF、PNG/JPG、Markdown、TXT，查询处理状态和版本 |
| 多模态入库 | 版面解析、必要的 OCR、图表区域提取、按需 VLM 描述、结构化切分 |
| 检索 | 文本 Dense＋BM25、RRF 融合、文本 Rerank、邻接与父级证据补全 |
| 图文问答 | 命中描述后读取原图，提供文档、页码和可用的区域引用 |
| 多轮交互 | 近期消息、历史摘要、当前文档范围与指代处理 |
| 工程交付 | Web 界面、API、持久化任务与数据、自动化测试、真实 API 评测 |

首版不包含音视频、Wiki 抓取、以图搜图、独立视觉向量检索、知识图谱、模型微调、多租户复杂权限及异常诊断。公式保留解析结果和原图，不承担专用数学推导系统的目标。跨文档问答只覆盖明确限定资料的证据整合，不承诺对整个知识库任意问题做穷尽总结。

“多模态”由图文资料处理及回答阶段实际读取图像体现。首版检索使用文字与图像描述的向量，不能表述为已经实现图片向量检索。

## 2. 参考资料与关键设计决策

### 2.1 课件的采用方式

| 参考资料 | 借鉴内容 | 本项目补充 |
| --- | --- | --- |
| Part 1：多模态 RAG 技术体系介绍 | 版面解析、图文关联、结构重建 | 以结构化元素为核心，明确图像描述与原始证据的区别 |
| Part 2：从零到一搭建引擎 | PDF 转 Markdown、检索工具、相关性判断和改写 | 保留原图读取能力，限制检索循环，正确处理本轮问题与历史指代 |
| Part 3：olmOCR 与 MinerU | OCR、元素解析、图像描述增强 | API 优先，按内容类型调用 VLM，记录质量和成本 |
| Part 4：项目开发实战 | FastAPI、流式回答、文档预览、接口分层 | 多文档管理、持久化、可恢复入库、原文定位和评测 |

本地课件仅用于学习方案和理解示例，不随仓库发布。模型版本、服务地址及依赖语法在实施时按官方接口验证，不直接沿用课件中的固定配置。

### 2.2 收束后的核心选择

1. **API 优先。** 使用文档解析 API 和通用视觉 API，不以本地部署大模型作为前置条件。
2. **结构化 JSON 为主，Markdown 为辅助。** 文档元素、阅读顺序、坐标和图文关系保存在结构化数据中，Markdown用于预览和导出。
3. **解析与理解分工。** 解析组件负责转录和结构恢复；VLM重点解释图表及截图，不对每段正文重复调用。
4. **检索代理与原始证据关联。** 图片描述用于检索，回答中的图像事实可以回到原图核查。
5. **先固定流程，再加入 Agentic 能力。** 先取得可复现的入库与问答基线，再验证动态检索是否带来收益。
6. **数据和测试先行。** 第一阶段即确定标注、评测单位和测试集，避免完成界面后再临时补测试。

OCR是一类任务，VLM是一类模型，二者不是互斥技术。olmOCR等解析模型本身就采用VLM架构；这里的“解析组件＋VLM增强”是按职责划分，不是假设底层必须使用两种完全不同的模型技术。

## 3. 总体架构与技术选型

### 3.1 四层结构

| 层级 | 职责 | 主要组件 |
| --- | --- | --- |
| 交互与接口层 | 文档管理、问答、引用预览、HTTP 与流式事件 | React＋TypeScript、FastAPI |
| 应用与编排层 | 入库任务、知识版本、问答流程、上下文和会话管理 | 应用服务、可选 LangGraph、单 worker |
| 核心能力层 | 解析适配、图表增强、切分、检索、重排、原图阅读 | Parser、VLM、Retriever、模型适配器 |
| 数据与基础设施层 | 元数据、文件、索引、任务和会话持久化 | PostgreSQL、Chroma、BM25磁盘索引、本地文件 |

```text
入库：Web上传 → API记录任务 → worker解析/增强/切分 → 构建索引 → 激活版本
问答：Web提问 → 查询解析与混合检索 → 图文证据补全 → Context Builder → 带引用回答
```

应用采用模块化单体，API和worker是两个进程，复用同一套业务模块；首版不拆微服务。

### 3.2 技术基线

| 模块 | 第一版选择 | 说明 |
| --- | --- | --- |
| Python环境 | Python 3.12、uv、锁文件 | 新工程独立环境，阶段0验证后锁定依赖 |
| Web后端 | FastAPI、Pydantic | 类型化接口，生成OpenAPI文档 |
| 前端 | React、TypeScript、Vite | 文档列表、解析预览、对话、原文查看 |
| 工作流 | 固定 RAG 问答流程；可选 LangGraph/LangChain 工具接口 | 基础问答不依赖异常诊断工作流，扩展时仍需限制工具和预算 |
| 文档解析 | MinerU解析API优先 | 验证Markdown、内容列表、图片和坐标的实际输出 |
| PDF辅助处理 | 本地PDF渲染、区域裁剪组件 | 实施时验证候选库，统一页码、旋转与坐标映射 |
| 对话模型 | 百炼API，初始候选 `qwen-plus` | 沿用旧工程调用经验，实际可用性在阶段0验证 |
| 视觉理解 | 百炼视觉API，初始候选 `qwen3-vl-plus` | 图表增强与查询时原图理解可共用模型，使用不同提示词 |
| Embedding | API模式 `text-embedding-v4` | 第一版只生成文本向量，维度初设1024并验证服务支持 |
| Rerank | API模式 `qwen3-rerank` | 复用旧工程选型思路，专属地址和请求格式独立验证 |
| 向量存储 | Chroma | 保存检索文本、文本向量与必要标识元数据 |
| 关键词检索 | bm25s持久化索引 | 构建时保存，进程加载时读取，不每次启动重新分词建库 |
| 业务数据库 | PostgreSQL | 文档、元素、版本、任务、会话、引用和评测信息 |
| 文件存储 | 本地目录 | 原始文件、页图、图表裁剪、解析原始产物 |
| 测试 | pytest、接口测试、浏览器端到端测试、评测脚本 | 规则验证与模型效果分开 |

模型名称为拟采用候选，不表示已经验证新工程账号、地域和接口权限。解析服务可能使用独立凭证；对话、视觉、Embedding和Rerank即使使用同一平台密钥，也必须按各自API协议调用。

新工程使用独立数据库（建议 `multimodal_rag`）、文件目录和Chroma集合，不复用旧工程的运行数据。实现初期由用户配置环境，凭证只放本地 `.env`。

### 4.2 完整数据先准备，模型调用分阶段验证

按用户确认，开发开始即准备完整资料，不再只下载100～200页子集。已下载锁定版本的两套完整公开仓库，共1672个文件、约2.13GB：ViDoRe两本PDF共1360页及全部页面图像、215个原始问题（六种语言共1290条）与6294条相关性记录；OmniDocBench完整1651页与官方标注。所有下载文件通过上游哈希核验。解析和模型API后续仍可分批验证，以控制成本，但不缩减完整数据基线。

同时准备独立的中文虚构工程回归资料：24份MD/TXT、60条问答（含12条限定范围无答案）与40条Agent工作流契约。它们由可重复的模板生成，明确标记synthetic及未人工全面审核，不能当作真实业务数据或公开基准。公开问答、解析评测和流程案例用途不同，不相加包装成一个问答集。

中文补齐已完整下载TiDB仓库2,849个文件，其中1,350份MD，筛出1,109份产品文档，建立12,122段原文证据。另将50篇完整源文重排为开发/测试两册PDF共322页，并准备12份TXT格式副本；均沿用源文分组，不作为新知识重复入库。180条候选覆盖概念操作40、配置30、表格30、图像30、跨文档30、无答案/澄清20。图像题经过助手看图起草，文本表格由源文抽取，均未冒充人工金标准。新增40条图文Agent契约及8条生命周期契约，详情见[中文主语料补齐说明](中文主语料补齐说明.md)。

已发现的解析集风险全部保留：54条越界多边形涉及26页；12张图片超过5000万像素。后续解析与评分适配器需检查像素预算、坐标变换和争议标注，不静默改写原始真值。当前没有模型评测成绩。

若官方相关性标注不完整，先标记可疑样本并人工复核；不能把所有未标注页面无条件视为错误证据。已提供的OCR Markdown可作对照，不能当作人工真值，也不能替代本项目的实际解析流程。

### 4.3 标注到原文，而不是绑定某一版Chunk

每条问答保存：问题编号、原始问题组编号、问题类型、语言、参考答案、可回答性、必要答案要点，以及证据的文档编号、物理页码、区域或原文片段。能区分“单个证据即可回答”和“多个证据需要联合使用”的样本，应分别标记替代证据与必要证据组。

切分后由程序将原文证据映射到Chunk，映射不明确的样本进入人工检查。这样更换解析器、切分长度或图像描述后，评测标准仍然稳定。数据集本身的 `corpus_id`、原始页码和系统元素编号之间保留映射表，PDF物理页码与书页印刷页码分开记录。

AI可辅助提出问题、补充同义表达及候选答案；审核时必须查看原始页面，特别核对表格数字、单位和图中关系。生成问答和参考答案不能进入知识检索索引。合成、人工审核、官方标注等来源分别记录。

中文证据定位到原文路径、标题与行号；表格保留表头/目标行，图像保留原图哈希，选定文档附保守PDF页范围。评测参考文档编号只供评分，不进入查询范围过滤。MD章节/图像指标与PDF页面指标分别记录，不直接混平均。

### 4.4 开发集和测试集

实际下载后校验了215组翻译问题及其证据一致性。按证据页连通分组时，其中182题形成大型关联组，作为开发集；其余33题作为锁定测试集。翻译版本随原始问题分组，因此对应1092条开发记录与198条测试记录。标注证据页在两侧不重叠。

严格按章节连通分组会得到214题和1题，不能形成有用的6:4划分。本版明确调整为证据页级隔离，两侧仍共享17个章节，不宣称章节/文档独立泛化。OmniDocBench按可识别来源文件名分组后固定哈希划分为996页开发、655页测试；UUID页面缺少可靠来源归属，划分局限保留在split_policy.json。中文模拟问答按主题划分40条开发、20条测试。

开发阶段使用开发集调整提示词和参数，测试集只用于阶段验收。测试资料本身可以存在于知识库中，不能泄露的是测试问题、参考答案及其评判信息。只有两份教材时，不声称完成严格的跨文档泛化验证，后续用外部数据另测。

TiDB中文资料先按相同文档内容及共享非装饰图片分组，再划分743份开发/366份测试文档，随后选取120/60条候选。多文档证据全部来自同侧，格式副本不跨侧；没有做语义近重复聚类，不宣称主题级泛化。人工审批独立记录，通过导出门槛后才生成正式gold子集。

## 5. 多模态知识入库

### 5.1 整体流程

```text
上传与去重 → 版面解析/必要OCR → 统一元素与原图关联
→ 按需VLM增强 → 结构感知切分 → 构建Dense和BM25索引 → 校验并激活知识版本
```

一份文档同时保存原始文件、解析结果、视觉增强和检索单元。原始证据与模型衍生描述分离保存，既能追溯错误，也能在切换模型或提示词时只重建受影响部分。

### 5.2 上传、检查与任务创建

上传时校验实际文件类型、大小、页数及文件是否可读，计算内容哈希。相同内容且处理配置未变时复用已有产物；同内容但解析器、提示词或切分配置变化时创建新的处理版本。首版输入上限暂定100MB、1000页，阶段0验证服务限制后调整；应用接收上限和外部服务单次处理上限分别控制。

API先持久化文档和任务，再返回任务编号。独立worker从PostgreSQL领取任务并执行，记录当前阶段、已完成页数、外部任务编号和错误原因。任务使用领取租约及心跳，进程退出后可以重新领取。远端任务超时优先查询已有任务状态，避免盲目重复提交付费解析。

页面阶段为 `queued → parsing → enriching → indexing → ready`，失败保留失败阶段。数据库执行状态继续使用`pending/running/succeeded/failed`，当前阶段单独记录；质量状态另设`candidate/needs_review/blocked`，不是执行成功就能发布。`ready`只能在质量处置和双索引校验后显示。上述worker与发布行为在阶段1实现，0B基础表尚无完整质量/审核字段。只报告真实阶段和可测的页数进度，不显示虚构的完成百分比。

### 5.3 文档解析与统一元素

PDF按页面处理。可靠文本层优先利用，扫描页或文字异常页执行OCR，复杂页面由版面解析器识别标题、段落、表格、图像和阅读顺序。MinerU适配器负责把服务输出归一化；不同服务模式是否真正支持按页路由，需要在阶段0确认，不假定所有API都提供相同控制参数。

每个元素至少保留：文档版本、元素编号、类型、页码、阅读顺序、章节路径、原始文字、原图引用、解析来源与可用的坐标。坐标归一化为页面左上角原点、范围0～1的矩形，并记录页面旋转与尺寸。多页单元保存多个来源片段，不用单一页码掩盖跨页情况。

图像优先按版面区域从渲染页面裁剪，以覆盖PDF矢量流程图、复合图表和截图；不能只提取内嵌位图对象。无可信区域坐标时回退到整页，界面显示页级引用。Markdown导出保留图像与表格引用，但数据库中的元素关系是正式来源。

### 5.4 OCR与VLM如何协同

| 内容 | 解析产物 | VLM策略 |
| --- | --- | --- |
| 正文、标题、列表 | 原文、层级、阅读顺序 | 默认不调用，异常识别结果才进入复核 |
| 普通表格 | HTML/结构化行列、标题、单位、截图 | 不重复让模型改写所有数值 |
| 复杂表格 | 原始结构、合并单元格信息、截图 | 辅助识别表头与解释含义，冲突时标记待核查 |
| 流程图、架构图 | 原图区域、图注、附近正文 | 提取节点、边、方向、条件和主体关系 |
| 曲线图、柱状图 | 原图、坐标轴、图例、标题 | 描述趋势和比较，无法精确读数时明确标注 |
| 操作截图 | OCR文字、原图、相关说明 | 描述操作对象与顺序 |

装饰图、重复Logo和明显无信息图片通过规则初筛；不能确定是否有用时保留原图，可延后增强。VLM输入包含目标区域、图注及有限邻近文字，必要时提供整页背景。

VLM输出采用结构化字段：内容类型、标题、可见文字、事实描述、可辨认关系、无法确认的细节及关联元素编号。提示词要求只根据提供资料描述，不补写文档外知识。不得把模型自报的置信度当成已校准正确概率。

解析得到的原文、表格值和VLM解释分别保存。若发现数值冲突、表格列错位或图像不可读，保留冲突标记并停止自动覆盖。第一版人工可在解析预览页检查并重新处理，完整标注编辑器留待后续。

### 5.5 切分与图文关联

正文沿用“章节优先、超长递归、同章节小块合并”的策略。每块保留标题路径与原始元素列表，禁止因合并而破坏来源映射。

小表格以完整单元参与检索；大表格按行组切分，每组附带必要表头、单位与表名，保留完整表格引用。跨页表格只有在标题、列结构及上下文均支持连续关系时合并；不确定时保存为相关单元，不强制拼接。

图片独立形成检索单元，正文为图注、OCR文字和带来源标记的VLM描述，原图保存在文件存储中。正文涉及“见图3”时记录相关元素关系，避免仅按同页关系绑定所有图片。图像描述不能与无关正文合并。

| 参数 | 初始值 | 约束 |
| --- | --- | --- |
| 文本块长度上限 | 600 Token | 长度统计需声明Tokenizer；编码包含标题等实际Embedding输入 |
| 递归切分重叠 | 80 Token | 只在同章节超长内容内使用 |
| 小块合并参考阈值 | 100 Token | 合并后仍满足长度上限与语义边界 |
| 图像描述长度目标 | 不超过400 Token | 复杂图可分描述单元，共用原图编号；不直接截断事实 |
| 邻接补全 | 前后各最多1块 | 按问题需要、章节关系与上下文预算决定 |

如果供应商未提供可复现Tokenizer，明确记录所用估算器及保守余量，并遵守模型输入上限；不把Python字符数直接称为Token数。

### 5.6 缓存、版本与激活

解析缓存由文件哈希、解析器和配置版本决定；视觉增强缓存还包含区域图像哈希、相关文字、模型与提示词版本；向量缓存包含完整Embedding输入哈希、模型和维度。不同处理版本之间不能误复用不兼容结果。

知识版本使用manifest记录包含哪些文档版本、处理版本、Chunk、Embedding配置及BM25配置。内容版本标识原文件；同一内容改变解析/切分配置时建立新处理版本，不与现有内容哈希唯一约束冲突。先构建未激活知识版本，验证质量处置、文件、元素映射、向量与关键词索引完整性，再通过PostgreSQL事务切换当前版本指针。Chroma和文件系统不参与同一个数据库事务，因此采用不可变产物＋指针切换实现发布一致性。处理版本、知识版本及质量字段将在1A起通过新增迁移补齐，不修改已应用的001迁移。

一次请求开始时固定知识版本，Dense、BM25、阅读工具和引用均使用该版本。删除或替换文档通过新manifest生效；历史版本至少保留到相关引用保留期结束。首版使用受控的显式清理命令，不自动删除仍被历史答案引用的文件。

## 6. 存储模型与职责

| 存储 | 保存内容 | 不承担的职责 |
| --- | --- | --- |
| PostgreSQL | 文档/版本、页面/元素、Chunk正文与关联、任务、会话、摘要、引用、运行元数据 | 不保存大批图片二进制，不承担首版向量检索 |
| Chroma | 文本向量、检索文本副本、知识版本及文档/Chunk/元素标识 | 不自动理解图片，不作为业务记录唯一来源 |
| BM25磁盘索引 | 与知识版本一致的分词结果、检索矩阵和Chunk映射 | 不混入测试问题、参考答案或不同版本语料 |
| 本地文件 | 原始PDF、页图、图表裁剪、表格文件、原始解析响应 | 不直接作为前端可任意读取的文件路径 |
| Postgres Checkpointer | 若启用：线程State与工作流快照 | 不替代业务消息表；不保证外部调用恰好执行一次 |

核心实体按“知识库 → 知识版本 → 文档版本 → 页面/元素 → Chunk”组织。Chunk可对应多个元素，每个元素携带原文定位信息。运行记录通过请求编号关联所用知识版本、检索结果、模型调用和最终引用。

PostgreSQL作为规范化内容和映射的权威来源，向量与关键词索引是可重建派生数据。图像和长文档通过受控资源接口返回，工具只接受服务生成的文档或元素编号。

首版不引入Elasticsearch：BM25是检索算法，不依赖某一种数据库；bm25s持久化文件已满足当前单worker和版本发布需求。Chroma虽能同时保存向量、文本和元数据，但不取代业务表的关联、约束与事务。0B已实现独立`multimodal_rag`库的四类基础表及迁移，尚未实现双索引与活动知识版本发布；未来规模扩大时再评估ES/OpenSearch，不提前增加运维组件。

## 7. 混合检索与图文证据构建

### 7.1 检索流程

```text
本轮问题与文档范围 → 必要的指代消解 → Dense/BM25并行召回
→ RRF融合与去重 → 文本Rerank → 按需阅读章节/原图 → 组织证据与引用
```

用户问题的版本号、代码、数字和限定条件必须保留。文档范围由用户选择及明确指代确定，模型不能默默扩展到其他知识库。内容类型通常作检索偏好，不因分类模型猜测而直接排除全部其他证据。

Dense对问题与检索单元生成同一模型、同一维度的文本向量，在Chroma中按配置的余弦距离检索。BM25对同一版本文本进行关键词检索，中英文分别处理并保留代码标识、数字、单位等完整形式。两路原始分数不可直接相加，使用RRF按排名融合。

RRF初始采用等权公式 `score(d) = Σ 1 / (60 + rank_i(d))`，排名从1开始，不在某路出现的文档不贡献该路分数。融合后按Chunk去重，再由文本Rerank对问题和候选文本打分。

| 检索参数 | 初始值 | 含义 |
| --- | --- | --- |
| Dense候选 | 20 | 每个查询最多返回20个Chunk |
| BM25候选 | 20 | 同上，两路使用同一文档范围 |
| RRF常数 | 60 | 等权融合，开发集验证后可调整 |
| 重排候选 | 20 | 从融合结果中取最多20个 |
| 基础Top K | 5 | 首次用于回答的候选证据种子 |

这些是实验起点。不同服务的距离、重排分数与是否可回答的判断不能共用固定阈值，阈值必须基于开发集校准。重排API不可用时可回退到RRF顺序，但必须标记降级，评测不能与完整流程混报。

### 7.2 原图与表格如何进入回答

检索可以先命中图注、OCR文字或VLM描述，再取对应的原图。如果问题要求读图中趋势、箭头关系或精确位置，调用视觉阅读工具，向VLM提供当前问题与原始图像；不只复述预生成描述。复杂表格问题可以取回完整表格或对应行组，再按需查看截图。

预生成描述是帮助定位的代理，原文和原图才是核查依据。文本Rerank只评价文字表示；没有执行原图阅读时，系统不能宣称完成视觉验证。若描述漏掉问题所需细节，可以读取已命中页面检查；若页面根本未被召回，原图阅读不能修复这类漏召回，这也是未来评估视觉索引的依据。

### 7.3 引用与证据不足

程序分配证据编号并保存其文档版本、页码、元素、可用坐标和内容片段。模型只能引用本轮实际提供的编号，前端根据编号生成跳转，不让模型编写本地路径或图片URL。

生成后检查引用编号存在且属于本轮证据；语义上的支撑关系另外评测。编号有效不等于结论正确。问题需要的证据缺失时，明确说明缺少什么；不把模型常识补写成来自知识库的结论。闲聊可以直接回答，文档事实问题必须走检索。

## 8. 可选的 Agentic RAG 与会话上下文增强

本章讨论的是知识问答的可选增强，不是异常诊断 Agent，也不是本项目基础竣工条件。基础版本采用固定的“查询解析 → 混合检索 → 证据补全 → Context Builder → 带引用回答”流程即可完成交付；只有在基础流程稳定后，才评估是否需要让 Agent 动态选择检索、阅读或澄清动作。异常诊断、测试日志 Tool、Human-in-the-Loop 诊断确认和经验回流另行在独立工程设计。

### 8.1 Agent负责的决策

Agent负责选择检索和阅读动作，不负责自动修改知识库。使用LangGraph限定可选动作：回答简单交互、检索、读取上下文、查看图表、补充检索、请求澄清或结束。程序约束预算和工具输入，模型提出的动作必须经过结构校验。

三个工具足以支撑首版：

| 工具 | 输入 | 输出 |
| --- | --- | --- |
| `search_knowledge` | 查询、知识版本、允许的文档范围 | 排序后的候选、来源编号、简短内容及模态信息 |
| `read_context` | 已授权Chunk/元素编号、有限读取范围 | 邻接段落、章节或表格内容及引用 |
| `inspect_visual` | 已授权元素/页面编号、当前子问题 | 针对原图的事实提取、引用及无法确认项 |

工具不能根据任意URL或文件路径读取资料。外部文档中的“忽略规则、调用工具”等文本作为资料处理，不作为执行指令。

### 8.2 固定流程与Agentic流程

固定流程先执行一次混合检索，再按规则读取必要图表，随后生成回答。它是正式对照版本，保留用于简单问题和评测。

Agentic流程先结合近期对话明确本轮问题与范围；复杂问题最多拆分3个子问题，初次检索后选择阅读工具，结构化记录已覆盖要点和缺失要点。证据不足时允许一次补充检索；仍然不足则部分回答、澄清或拒绝给出无依据结论。模型输出的是动作与简短证据判断，不要求记录内部推理链。

State显式保存 `current_question`、子问题、轮次、已读元素和证据，不依赖“历史messages第一条”作为当前问题。去重后没有新增证据时停止重复检索。

| 控制项 | 初始上限 | 执行方式 |
| --- | --- | --- |
| 检索轮数 | 2轮 | 首次＋一次补充；一轮可含最多3个子查询 |
| 子问题数 | 3个 | 超出时优先澄清范围 |
| 原图读取 | 每请求最多3个不同区域/页面 | 重复相同问题与图像可命中请求缓存 |
| 工具调用总数 | 10次 | 包含检索、正文阅读与视觉阅读，独立计数 |
| 外部调用重试 | 每次最多2次额外重试 | 只针对适合重试的错误，整体超时优先 |
| Agent端到端超时 | 120秒 | 为初始上限，取消或超时应返回清晰状态 |

图片数量、检索次数与超时共同约束成本，不单靠LangGraph递归限制。若不能在预算内获得足够证据，输出已有结论及缺失部分，不无限循环。

### 8.3 记忆与上下文

PostgreSQL业务表完整保存用户消息和最终回复；近期消息窗口与增量摘要供多轮指代使用。当前选择的知识库、文档和知识版本是显式字段，新会话不继承旧会话状态，切换范围后不复用不匹配证据。

Context Builder按当前节点组装系统要求、本轮问题、必要的摘要/近期对话和本轮证据。历史助手答案不是新的文档事实来源，历史图像默认不反复输入。文本上下文初设8000 Token、输出预留2000 Token，实际还需按模型窗口扣除系统、工具Schema和图像消耗；视觉Token以供应商用量为准，不能用文字估算器代替。

采用Checkpointer时只在State中保存必要结构和证据引用，避免把所有原图、候选列表或巨大响应放进检查点。重启恢复不等于外部调用绝不重复，模型和工具请求仍需幂等标识与缓存。大块临时内容不进入State，因此也不会先被快照保存、最后才清除。

## 9. Web体验与接口约定

### 9.1 三个主要页面

**文档管理页**展示知识库、文档、当前版本、解析任务和失败原因，支持上传、重试与明确的版本切换。用户能区分“已上传”“处理中”和“可以检索”。

**解析预览页**并排展示原始页面和正文/表格/图像解析结果，标出相关区域，允许查看VLM描述及识别异常。它也是定位OCR错误、图文错配和切分问题的学习与调试入口。

**知识问答页**提供文档范围选择、流式回答、图片/表格证据卡片和原文跳转。图表问题可展示实际使用的原图。检索轮次、工具动作、耗时等信息放在可折叠面板中。

### 9.2 主要接口

| 接口 | 用途 |
| --- | --- |
| `POST /api/v1/documents` | 上传文件，返回文档和任务编号 |
| `GET /api/v1/ingestion-jobs/{job_id}` | 查询真实处理阶段、进度及错误 |
| `POST /api/v1/ingestion-jobs/{job_id}/retry` | 从可恢复阶段重试 |
| `GET /api/v1/documents/{document_id}/pages/{page}` | 获取版本化原页与元素信息 |
| `GET /api/v1/elements/{element_id}` | 获取元素、来源及受控资源引用 |
| `POST /api/v1/knowledge-versions/{version_id}/activate` | 校验后切换版本 |
| `POST /api/v1/retrieval/search` | 对外提供可单独评测的检索能力 |
| `POST /api/v1/chat` | 提交会话请求并流式返回回答 |
| `GET /api/v1/sessions/{session_id}/messages` | 查询持久化历史 |
| `GET /health/live` | 应用存活检查，0A已实现，不调用外部服务 |
| `GET /health/ready` | 完整服务就绪检查；0A明确返回503，后续接入依赖后扩展 |
| `GET /api/v1/dependencies` | 配置状态检查，0A已实现；不代表真实连通 |
| `POST /api/v1/preview` | 0A开发白名单文本结构预览；不写数据库或索引 |

具体请求Schema在阶段0/1锁定，统一包含请求编号和结构化错误。流式聊天用浏览器 `fetch` 读取POST响应的事件流，事件包括 `status`、`citation`、`token`、`done`、`error`；每个数据负载按JSON编码。流中断时报告未完成，不静默重复拼接第二段完整回答。

首版默认本机使用，后端CORS限定开发前端来源。完整用户权限和公网部署是后续事项。

## 10. 测试与评测设计

### 10.1 四层测试目标

| 层面 | 主要问题 | 核心度量或检查 |
| --- | --- | --- |
| 入库解析 | 原文是否被正确保留？ | 文字CER、表格关键值正确率、图文/页码关联正确性 |
| 检索 | 正确证据是否被召回并排在前面？ | 页面级Recall@5、nDCG@5及模态分类结果 |
| 回答 | 证据是否被正确理解和引用？ | 答案要点正确性、引用支撑率、无答案拒答正确性 |
| Agent与工程 | 动作合理、受控且稳定吗？ | 工具参数和范围、必要证据覆盖、预算终止、超时/重试与会话隔离 |

所有层面记录耗时与API用量。模型服务报告的Token和账单估算分开；价格未配置时输出调用量，不伪造费用。性能报告包含样本量、中位数及P95，并说明缓存冷暖和并发条件。

### 10.2 入库如何测

先建立小规模人工可检查页面，再用OmniDocBench子集扩大覆盖。文字CER基于标注文本计算，预先声明空白、大小写和标点归一化规则。表格检查数字、单位及行列表头对应关系，不能只比较扁平文本是否包含相同数字。图文关联检查图号、图注、元素位置和来源页面是否一致。

规则测试覆盖同一文件重复上传、解析失败重试、坐标缩放与旋转、跨页元素、超长内容、空文件及版本切换。VLM增强重点核查是否遗漏重要关系或补写不存在的事实，纯字符串相似度不能替代这项检查。

### 10.3 检索如何测

系统返回Chunk，公开数据通常提供页面相关性；评测适配器将Chunk映射到原始页面，按预先固定的聚合规则生成去重页面排序，再计算页面指标。对一个Chunk涉及多个页面的情况，只映射其确实覆盖的来源页面；同分时使用确定性排序规则。

页面排序初始采用该页命中Chunk的最高最终排序分数，取前5个不同页面。`Recall@5 = 前5页命中的相关页数 / 标注相关页总数`，逐题计算后宏平均；需要超过5页的问题仍按定义计算，同时单独报告其数量和完整证据覆盖情况。

nDCG@5使用数据源明确的相关性等级。必要证据页和完整答案页不能不加说明地混成相同标签。若补充数据只有二元标签则单独说明，并按同一规则计算。邻接与原图扩展后的实际证据另外统计，不能把扩展后超过5页的结果仍称为Recall@5。

数据集带来的预解析文本只是对照输入。正式端到端成绩使用本工程从原始文件解析的结果，并保存知识版本、候选排序及页面映射，支持复算。

### 10.4 回答如何测

数值型和短答案优先程序核验，检查单位和必要条件；开放式答案使用固定评分标准与LLM初评，并人工抽查、复核争议和失败样本。评判模型查看原文或原图，不能只根据待评系统自己的图片描述判断其正确性。

引用支撑率评估“结论是否被所引证据支持”，不仅检查引用存在。无答案案例检查是否恰当拒答或说明缺失信息，同时检查可回答问题是否被过度拒答。

增加一组“直接提供标准证据”的回答测试：若标准证据下仍答错，优先检查视觉理解、生成和上下文；若标准证据能答对而端到端答错，重点检查入库与检索。该结果与端到端结果分别报告。

### 10.5 Agent工作流如何测

| 场景 | 预期行为 |
| --- | --- |
| 简单正文问题 | 检索后回答，无不必要的视觉调用 |
| 图中关系或趋势 | 定位并读取相应原图，不只引用文件名 |
| 多页比较 | 覆盖必要证据，允许合理的多种工具顺序 |
| 首轮缺少证据 | 只针对缺失内容补充检索，受轮次预算约束 |
| 无答案或歧义 | 拒答、部分回答或澄清，不重复循环 |
| 新会话/切换文档 | 不带入旧范围中的证据 |
| API超时、限流、重复请求 | 有限重试，消息与任务不重复写入，错误可定位 |
| 文档包含指令性文字 | 按文档内容处理，不据此越过工具和知识范围 |

工具测试标注允许动作、必要动作和禁止动作，不把唯一固定轨迹当成所有问题的正确答案。Mock验证流程与边界；真实API测试验证模型是否实际做出正确决策，两类结果分开保存。

### 10.6 技术演进与对照实验

| 版本 | 变化 | 验证目标 |
| --- | --- | --- |
| V0 | 基础文本提取＋结构切分＋混合检索，单轮问答 | 建立独立新工程的文本基线 |
| V1 | 加入版面/OCR与表格结构 | 验证扫描页、表格及来源恢复的价值 |
| V2 | 加入VLM描述＋查询时原图理解 | 验证图表证据的召回和理解收益 |
| V3 | 在V2上加入受控Agentic检索 | 验证困难问题改善是否值得额外调用成本 |

对照尽量固定语料、问题集、Embedding、Rerank和预算。V0/V1可使用同一支持视觉的生成模型但仅传文字，V2再增加图片输入，以减少模型更换带来的干扰。V2同时引入描述和读图，不能将总收益全部归因于某一项；必要时在小规模困难集上增加“仅描述”和“描述＋读图”对照。

V3同时报告简单问题和复杂问题的结果，不能以总体提升掩盖简单问题的延迟恶化。锁定测试集用于验收，不把多次测试中的最好一次当作稳定效果；对关键Agent案例可重复运行，记录波动。

### 10.7 运行记录与结果表达

每次评测保存：代码提交号、数据manifest、问题split、知识版本、解析器/模型/提示词版本、参数、调用记录、候选证据、答案、评分与错误分类。模型若只提供可变别名，应记录别名和调用日期，并说明无法完全锁定服务端版本。

失败样本至少分类为：解析缺失、结构/图文错配、召回遗漏、排序不当、原图理解错误、证据组装遗漏、生成错误、工具/路由错误、基础设施失败和标注问题。

简历和项目报告只引用真实运行结果，写明子集规模、评测单位及对照条件。本阶段不设置虚构的性能目标；取得基线后再确定需要达到的效果门槛。

## 11. 工程组织与配置规范

### 11.1 计划目录

以下是后续实现目标，不表示这些目录和代码已创建。

```text
multimodal-rag-platform/
  README.md
  docs/                       # 设计、阶段验收与决策记录
  backend/
    src/multimodal_rag/
      api/                    # 路由和请求/响应Schema
      application/            # 入库、问答、知识版本与会话服务
```

保持四层职责即可，第一版不过度细分包和通用框架。核心层通过接口使用模型与存储，不在切分、检索或工作流中硬编码API地址。类型、注释和错误信息优先服务学习与排障。

### 11.2 配置

`.env`统一存放运行配置与凭证，`.env.example`只放说明和无密钥示例。用Pydantic Settings校验必需字段。参数分为应用/路径、PostgreSQL、Parser、Chat/VLM、Embedding/Rerank、切分检索、Agent预算和评测配置。

公开、非敏感的评测参数使用版本化配置文件记录，避免仅凭开发机`.env`无法复现实验。每次运行导出脱敏后的有效配置及哈希，API密钥和数据库密码不能进入运行报告。

## 12. 开发阶段与验收

| 阶段 | 主要工作 | 必须交付及验收 |
| --- | --- | --- |
| 0：数据和接口验证 | 完整数据已准备；接下来验证解析、视觉、Embedding及Rerank API | 完整数据manifest及离线验收报告；后续10～20页代表样本的真实API输出、错误清单和调用记录 |
| 1：多模态入库 | 工程骨架、数据库、worker、解析适配、VLM增强、切分与版本索引 | 多文件完整入库；重试不重复生成有效记录；原文定位可核查；版本切换一致；初版解析评测 |
| 2：固定流程问答 | 混合检索、图文阅读、上下文、引用与基础Web联调 | 文本/表格/图像案例可演示；真实检索与回答报告；证据不足处理；文档→问答端到端测试 |
| 4：产品与交付 | 已准备语料的完整处理、Web体验、回归测试、锁定测试集评测、部署说明 | 干净环境可按文档运行；完整演示；数据来源说明；真实评测和已知限制 |

前端按阶段逐步交付：阶段1先做上传/状态/解析查看，阶段2加入问答与引用，阶段3增加折叠的工具轨迹。每个阶段都保留可运行版本和失败案例，不等所有功能完成才联调。

阶段0若发现API不能提供可靠坐标，应记录页级降级能力，并决定是否用辅助版面组件补齐；模型或服务替换写入设计决策记录。因效果不佳而改变方案时，保留触发改进的样本及前后输出，不凭经验描述成已验证收益。

## 13. 后续扩展触发条件

| 后续能力 | 何时值得做 |
| --- | --- |
| 独立视觉向量检索 | 图像描述持续遗漏查询所需信息，导致页面无法被召回，并已有明确失败集 |
| 另一解析器/olmOCR对照 | 主解析服务在特定版式上持续失败，或成本/依赖条件不合适 |
| 表格计算工具 | 评测中出现大量确定性求和、比例或比较，模型直接算数不稳定 |
| 对象存储与多worker | 本地磁盘、任务排队或并发已成为可测瓶颈 |
| 其他新领域数据 | 中文技术主语料与英文基准稳定后，再验证跨领域泛化 |
| 异常诊断Agent接入 | 作为独立项目开发；本平台只需提供稳定的检索/问答接口 |

每次扩展都先明确要解决的失败类型，再增加一个可验证能力。新项目的主要价值落在“复杂资料如何可靠入库、如何找齐图文证据、如何用测试推动改进”。
