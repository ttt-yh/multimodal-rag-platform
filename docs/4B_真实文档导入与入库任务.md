# 阶段4B：真实文档导入与入库任务

## 1. 本阶段目标

把知识库页面上的“导入资料”从占位按钮变成一条真实可执行的入库路径：用户从项目白名单中选择 Markdown/TXT 文档，系统创建 PostgreSQL 入库任务，调用现有单 worker 完成解析和质量检查，页面展示任务阶段与结果。

本阶段仍然遵守安全边界：浏览器不上传任意本地路径，也不直接修改向量索引。文档必须先登记在 `data/manifests/ingestion_chinese_md.jsonl` 中，后端在排队和解析前分别校验文档编号、路径、格式、大小、UTF-8 编码和 SHA-256 哈希。

## 2. 处理流程

```text
读取白名单目录
  → 用户选择文档
  → 创建 pending 入库任务
  → API worker 领取并解析文档
  → 结构化元素持久化到 PostgreSQL
  → 质量检查完成（quality_checked）
  → 页面显示任务状态
  → 人工审核通过后，才允许构建/激活索引
```

解析完成不等于文档已经可检索。任务成功只说明原文和解析产物已经持久化，后续仍需质量审核、Embedding/BM25 构建和索引激活。

## 3. 接口设计

| 接口 | 作用 |
| --- | --- |
| `GET /api/v1/ingestion/catalog` | 返回白名单中的可导入 Markdown/TXT 文档元数据 |
| `POST /api/v1/ingestion/jobs` | 根据 `document_id` 创建幂等入库任务 |
| `POST /api/v1/ingestion/jobs/{job_id}/run` | 当前单 worker 开发模式下，显式处理一个任务 |
| `GET /api/v1/ingestion/jobs/{job_id}` | 查询任务状态、阶段、质量状态和错误编号 |

`POST /api/v1/ingestion/jobs` 的请求只包含文档编号，不接受客户端路径。任务创建由已有的 `enqueue_document` 完成，同一内容和处理配置重复提交时复用幂等键；`run` 接口使用唯一 worker 编号领取任务，执行已有的解析、质量判断和持久化逻辑。

## 4. 前端交互

知识库页面新增“导入资料”按钮。弹窗打开时读取白名单目录，用户选择文档后点击“开始入库”；页面先显示任务排队状态，再展示处理阶段、错误编号或“解析完成，等待质量审核和索引发布”。任务状态条不会把 `quality_checked` 误显示为“已激活”，避免让使用者误以为新文档已经进入当前检索索引。
