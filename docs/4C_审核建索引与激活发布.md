# 阶段4C：审核、建索引与激活发布

## 1. 设计目标

入库任务完成后，文档不能直接进入线上检索。系统把后续流程拆成三个明确步骤：人工审核处理版本、构建草稿 Dense/BM25 索引、通过完整性校验后激活索引。每一步都有独立接口和状态，避免解析成功被误认为已经发布。

## 2. 页面流程

```text
审核队列
  → 查看元素/Chunk/警告数量
  → 提交 approved 或 rejected
  → 勾选已审核处理版本
  → 填写Embedding调用预算并确认
  → 构建 draft 索引
  → 核对 Chunk / Vector / BM25 数量
  → 确认激活
```

知识库页面新增两个面板：

- **审核队列**：展示处理版本、文档标题、Chunk 数量、警告数量和质量状态；只有 `approved` 版本可以被勾选用于建索引。
- **索引版本**：展示索引状态、Embedding 模型、Chunk/Vector/BM25 三类数量；draft 索引需要再次确认后才可激活。

## 3. 后端接口

| 接口 | 作用 | 外部调用 |
| --- | --- | --- |
| `GET /api/v1/review-queue?state=all` | 查询待审核或已审核处理版本 | 无 |
| `POST /api/v1/processing/{id}/review` | 记录人工审核结论和说明 | 无 |
| `GET /api/v1/indexes?status=all` | 查询索引版本和构建状态 | 无 |
| `POST /api/v1/indexes/build` | 按处理版本范围构建 draft 索引 | 会调用 Embedding |
| `POST /api/v1/indexes/{id}/activate` | 校验并切换当前 active 索引 | 无 |

索引构建接口必须同时满足两个条件：请求携带 `confirm_live=true`，并提供足够的 `max_requests` 预算。没有明确确认时，接口返回 `live_confirmation_required`，不会发起外部请求。激活接口必须携带 `confirm=true`，并由 `activate_index` 统一校验：处理版本全部审核通过、Chunk/Vector/BM25 数量一致、索引产物目录存在且位于项目目录内。

## 4. 审核与发布的职责边界

人工审核只修改 `processing_versions.quality_status` 并记录 `quality_reviews`；它不会自动构建索引，也不会自动改变当前 active 索引。索引构建只产生 draft 产物；只有激活成功后，检索服务才会读取新的索引版本。旧 active 索引会被标记为 retired，保证任意时刻只有一个全局可读索引。
